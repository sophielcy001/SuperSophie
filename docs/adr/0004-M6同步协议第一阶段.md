# ADR 0004 · M6 同步协议第一阶段

日期：2026-11-24 · 状态：已采纳

## 背景

1.0（M0–M5）的功能已经完成，只剩 A18 正式性能采样，需要 16 GiB Windows x64 实体参考机。用户确认的下一个方向是自托管同步，对应计划中的 M6／K25。计划第 5.4 节要求：由服务端确定提交顺序，客户端按 `base_revision` 发送离线操作；同一对象冲突时保留双方，不做静默的最后写入覆盖；不把运行中的 SQLite 文件放到网盘或 NAS 上让多台设备共同写入；首次联网就要有认证与传输保护。

## 决定

1. **对象级快照同步。** 一个页面就是一个对象，每次推送该页面的完整同步字段。不引入 CRDT（实时协作留到 M7 单独选型）。
2. **服务端排序，按版本判定冲突。** 服务端为每个对象维护单调递增的 `version`，全局 `seq` 决定拉取顺序。`baseVersion` 与服务端版本不符即为冲突，客户端保留冲突副本。
3. **Core 不联网。** Core 只负责生成请求和应用响应，每一步都是一个本机事务，传输层由桌面端或测试实现。这样 Core 的测试不依赖网络，也便于以后替换传输方式。
4. **协议放在独立 crate。** `zhiye-sync-protocol` 只依赖 serde，Core 与服务端共用，服务端不依赖 Core。
5. **幂等提交。** 客户端把待确认的操作存入 `sync_outbox`，内容不变时复用 `opId`。服务端按「设备 + `opId`」保存已接受的结果并校验请求摘要。
6. **删除从宽。** 对端的永久删除在本机只移入回收站；本机有未发送修改时保留修改。宁可多留数据，也不误删。
7. **第一阶段只同步普通页面。** 数据库、记录、附件和封面牵涉 Schema 版本、关系镜像、派生计算和原件传输，各自需要单独的冲突规则，后续分阶段加入。被排除的页面会在状态中逐项列出，不会静默遗漏。
8. **参考服务暂用 SQLite。** 先以 SQLite 验证协议和引擎。计划指定的 PostgreSQL 适配与 Docker Compose 部署放到后续阶段。服务只提供 HTTP，默认只监听回环地址；监听其他地址时必须显式声明前面有 HTTPS 反向代理。
9. **数据格式升到 22。** 新增四张同步表，沿用既有的「先备份再迁移」流程。整库恢复出的副本清空同步状态。

## 影响

- 0.50.14 及更早版本不能打开格式 22 的工作空间，按既有规则提示版本过低；升级前的备份可以用旧版恢复。
- 同步写入的远端变化和本机编辑一样生成修订，因此历史、搜索、反向链接和集成变更流无需特殊处理。
- 同一页面的并发修改以整页为单位冲突，即使双方改的是不同的块。块级合并留给 M7 的实时协作选型。

## 补充（2026-11-24）：附件随页面同步

决定 7 中「附件和封面暂不同步」已调整：

- 页面快照增加 `attachments` 和 `cover`。原件按 SHA-256 单独上传和下载，服务端拒绝引用了未上传原件的推送。
- 是否有改动改为比较同步状态的指纹，以覆盖添加附件、改名这类不产生修订的变化。为免两台设备因序列化细节而反复推送，记录的一致状态默认取写入后的本机快照；只有本机保留了服务端没有的内容时，才取服务端快照。
- 附件只增不删，与历史修订保持一致。

数据库与记录仍按原决定留在本机。

## 补充（2026-11-24）：数据库与记录

决定 7 中「数据库、记录暂不同步」也已调整：

- 新增对象类型「数据库定义」（动作 `collection`），内容为容器页、属性定义和视图。记录仍是页面对象，快照带上属性值和创建时间。
- 写入远端记录时不做成对关联的镜像传播，因为对端产生的镜像修改会作为独立对象到达；在本机再做一遍会被误判为编辑冲突。
- 互相关联的记录可能在同一批到达。同批即将写入的记录先视为有效的关联目标，写完后检查有无悬空的关联边；如有，回滚整批，去掉没能写入的目标后重试。
- 两端同时修改同一数据库定义时按属性 ID、视图 ID 合并，而不是另存副本，因为数据库定义没有可以独立存在的「副本」。

模板仍只在本机。

## 补充（2026-11-24）：PostgreSQL 与 Docker 部署

决定 8 中「PostgreSQL 与 Docker Compose 放到后续阶段」已完成：

- 服务端拆出存储层，SQLite 与 PostgreSQL 两种实现共用同一套业务规则（版本判定、幂等重放、原件检查），服务端测试在两种存储上各跑一遍。
- PostgreSQL 使用同步客户端，连接在出错后自动重建；推送事务按工作空间加 advisory 锁，保证变更序号按提交顺序出现，拉取时不会跳过变更。
- 参考部署为 PostgreSQL、同步服务、Caddy 三个容器。TLS 由 Caddy 负责；同步服务本身仍只提供 HTTP，并且不对外发布端口。数据库密码与管理令牌以 Docker secrets 文件挂载，不出现在环境变量或命令行里。
- 附件原件仍保存在文件卷中，对象存储适配留待需要时再做。
