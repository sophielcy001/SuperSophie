# 自托管个人同步（M6 第一阶段）

本文说明 M6 自托管个人同步的第一阶段：同步协议 1、参考服务 `zhiye-sync-server`、Core 同步逻辑和桌面端的「同步」设置。范围以[完整开发计划](../个人资源管理系统_完整开发Plan_v2.0.md)第 5.4 节和 M6 为准，设计取舍见 [ADR 0004](adr/0004-M6同步协议第一阶段.md)。

尚未完成的部分见文末。

## 在桌面程序中使用

1. 按下文「参考服务」部署同步服务，并在前面配置 HTTPS 反向代理。
2. 打开工作空间菜单 → 「同步」，或在命令面板输入「同步」。
3. 在「本机设备」中填写服务地址、管理令牌和本机名称，选择「登记本机」。管理令牌只用于这一次登记，不会保存。本机收到的设备令牌保存在 Windows 凭据管理器或 macOS 钥匙串，服务地址和设备 ID 写在数据目录的 `sync-device.json`。
4. 在当前工作空间下选择「启用同步」。知页会在服务中登记该工作空间并立即同步一次。之后程序运行时每 5 分钟自动同步，也可以随时选择「立即同步」。
5. 在另一台电脑上同样登记本机，然后在「服务中的工作空间」中选择「查看」→「加入本机」，在本机创建同一个工作空间的副本。

服务地址必须以 `https://` 开头。只有本机测试服务（`127.0.0.1`、`::1` 或 `localhost`）可以使用 `http://`。证书由系统校验，因此系统信任的自建 CA 证书也可以使用。请求不跟随重定向，以免把令牌发送到其他主机。

「同步」窗口显示上次成功的时间、待上传数量、已同步页面数和上次失败的原因。冲突会逐项列出，并可直接打开原页面或冲突副本。另一台设备的修改写入本机后，页面树会刷新；如果当前打开的页面没有未保存的修改，正文也会刷新。正在编辑的页面被同步更新时，界面会提示，保存时按原有流程对比两个版本。

「停用同步」只是暂停自动同步，下次启用时从原来的进度继续。启用时如果本机已改登记到另一个服务，这个工作空间会从头上传到新服务。「移除本机凭据」会删除本机的令牌和设置，本地资料不受影响；要彻底停用旧令牌，请在服务中撤销这台设备。

## 同步范围

协议 1 按对象同步。对象有两种：页面（含数据库记录），对象 ID 就是页面 ID；数据库定义，对象 ID 就是数据库 ID。页面同步的字段有：

| 字段 | 说明 |
|---|---|
| `parentId` | 上级页面。对端缺少上级时，该变化先暂存，等上级到达后再写入 |
| `title`、`icon` | 标题与图标 |
| `blocks` | 原生正文块，块 ID、未知块和页内引用原样保留 |
| `trashRootId` | 回收站状态，与本机回收站使用同一种标记 |
| `attachments` | 本页的附件：ID、名称、SHA-256、大小、类型和添加时间。原件按 SHA-256 单独传输，见下文「附件原件」 |
| `cover` | 封面，引用本页的图片附件 |
| `record` | 仅数据库记录有：创建时间，以及按属性 ID 保存的属性值（与本机存储格式相同） |

以下页面暂不同步，留在本机，并在 `sync_status` 的 `skipped` 中列出：

| 原因代码 | 内容 |
|---|---|
| `ORIGINAL_MISSING` | 本机找不到某个附件的原件，例如原件文件被手动删除。原件恢复后会自动同步 |
| `PARENT_SKIPPED` | 上级属于以上情况的页面 |

页面模板和数据库记录模板只保存在本机，不参与同步。

### 数据库

- **数据库定义**作为独立对象同步，包括容器页 ID、属性定义（含关联、汇总和公式）和保存的视图。容器页本身作为普通页面同步，「数据库说明」就是它的正文。本机的定义修订号不同步，收到远端定义时在本机递增，已打开的编辑面板会因此提示重新打开。
- **记录**作为页面同步，并带上属性值和创建时间。记录不能改到别的数据库下。
- **发送顺序**：容器页 → 数据库定义 → 记录。顺序乱了的变化会暂存，前置对象到达后再写入。
- **关联**：关联边由本机根据属性值重建。写入远端记录时不再做成对关联的镜像传播，另一侧记录的变化会作为独立对象到达。同一批到达的记录可以互相关联；关联的目标不在本机、也不在这一批里时，引用它的记录暂存，原因为「关联的记录尚未同步到本机」。
- **派生数据**：汇总、公式和全文索引都在本机重新计算，不经过同步传输。

## 工作方式

服务端按接收顺序为每次变更分配全局递增的 `seq`，并为每个对象维护版本号 `version`。客户端提交时带上本次编辑所依据的 `baseVersion`：

- `baseVersion` 等于服务端当前版本时接受，版本加 1。
- 版本不符时返回 `conflict` 和服务端当前状态，不覆盖较新的内容。
- 新对象使用 `baseVersion = 0`；对象已存在时同样返回冲突。

一次同步依次执行：拉取 → 推送 → 再拉取。Core 不发起网络连接，由调用方负责传输：

```text
Store::sync_status(ws).cursor            → GET  /v1/workspaces/{ws}/changes?since=…
Store::sync_apply_pull(ws, &response)    ← 写入远端变化，推进游标
Store::sync_prepare_push(ws).request     → POST /v1/workspaces/{ws}/push
Store::sync_apply_push(ws, &response)    ← 记录服务端版本
```

每一步在一个本机 SQLite 事务内提交。网络中断后重复同一步即可：

- 未发送的操作保存在 `sync_outbox`，内容不变时沿用原 `opId`。
- 服务端按「设备 + `opId`」保存已接受的结果，重放时返回同一回执，不会重复创建。同一 `opId` 配上不同内容时返回 `409 OPERATION_REUSED`。
- 同一份回执应用两次不产生变化。

写入远端变化时，每个远端版本在本机生成一条普通修订，历史、反向链接、全文索引和集成变更流都会照常更新。

是否有待上传的改动按页面同步状态的指纹判断，而不是按修订号。因此不产生新修订的改动也会同步，例如添加附件或给附件改名。

### 附件原件

- 推送前，客户端用 `POST …/blobs/missing` 查出服务端缺少的原件，逐个用 `PUT …/blobs/{sha256}` 上传。服务端校验 SHA-256，并拒绝引用了未上传原件的推送（`409 BLOB_MISSING`）。
- 拉取后、写入前，客户端用 `Store::sync_missing_blobs` 查出本机缺少的原件，下载后用 `Store::sync_store_blob` 校验并保存。
- 原件按内容寻址，服务端和各设备都只保存一份，相同文件不会重复传输。
- 某个原件暂时无法下载时，只有引用它的页面进入 `sync_pending`，其他页面照常写入。
- 当前版本在同步时就下载全部原件，尚未做到打开时才按需下载。

## 冲突处理

冲突不做静默的最后写入覆盖。结果出现在 `SyncReport.conflicts`：

| 类型 | 情形 | 结果 |
|---|---|---|
| `EDIT_EDIT` | 两台设备离线修改了同一页面或同一条记录 | 原页面采用服务端版本；本机版本另存为「标题（冲突副本）」，块 ID 重新生成，附件复制一份并改写正文、封面和附件属性中的引用，在下次推送时上传。记录的冲突副本留在同一个数据库，但去掉关联值，以免出现只有一侧的关联。本机原修订也留在该页历史中 |
| `DELETE_EDIT` | 对端永久删除了本机修改过的页面 | 保留本机页面，下次推送时在服务端重新创建 |
| `EDIT_DELETE` | 本机永久删除了对端修改过的页面 | 恢复对端修改后的页面，撤回本机未发送的删除 |
| `PARENT_CYCLE` | 两台设备交叉移动页面，合并后会形成循环 | 后到的页面移到顶层，并把该位置推送给其他设备 |
| `SCHEMA_MERGED` | 两台设备都修改了同一个数据库的属性或视图 | 按属性 ID 和视图 ID 合并：两边都有的以服务端为准，只在本机的保留并推送回去。`pageId` 为容器页 |
| `REJECTED` | 推送时服务端已有更新版本 | 下次拉取会带回服务端版本，再按以上规则处理 |

对端永久删除了本机没有改动的页面时，本机只把它移入回收站，不会直接抹去。之后在本机清空回收站，也不会再次发送删除。

附件按 ID 合并：远端新增的附件写入本机，改名会覆盖本机名称；附件从不因同步而删除，因为历史修订可能还引用它们。只有本机有的附件会随下次推送上传。两台设备给同一页添加了同名、同内容的附件时，后到的那份会改名为「名称 (2)」。

暂时无法写入的远端变化（缺少上级页面、块 ID 仍被本机其他页面占用等）放在 `sync_pending`，并附原因。每次拉取都会重试；同一次拉取中，在后续变化到达后也会立即重试。

## 参考服务

### 用 Docker Compose 部署（推荐）

[`deploy/sync`](../deploy/sync) 提供三个容器：PostgreSQL 17 保存变更日志，同步服务处理请求，Caddy 负责 HTTPS 并转发到同步服务。同步服务和数据库都不对外发布端口。

1. 把仓库放在服务器的本地磁盘上，进入 `deploy/sync`。网络共享盘往往不支持文件权限，密钥目录就无法限制为只有当前用户可读。
2. 运行 `sh init-secrets.sh`。它生成数据库密码 `secrets/postgres_password` 和管理令牌 `secrets/admin_token`（各 48 个字符），并从 `.env.example` 复制出 `.env`。已存在的密钥不会被覆盖。
3. 编辑 `.env`：
   - `ZHIYE_SYNC_DOMAIN`：服务的域名。公网域名会由 Caddy 自动申请 Let's Encrypt 证书，需要 80 和 443 端口能从外网访问。
   - 内网或测试：设 `ZHIYE_SYNC_CADDY_OPTIONS=local_certs`，证书改由 Caddy 自建的 CA 签发；域名为 `localhost` 时会自动这样处理。
   - `ZHIYE_SYNC_HTTP_PORT`、`ZHIYE_SYNC_HTTPS_PORT`：主机上的 80、443 已被占用时可以改用其他端口。改用其他端口后，从 HTTP 跳转到 HTTPS 时会丢掉端口号，请在桌面程序中直接填写带端口的 `https://<域名>:<端口>`。
4. 运行 `docker compose up -d --build`。第一次需要编译同步服务，约需几分钟。
5. 在桌面程序的「同步」中填写 `https://<域名>` 和 `secrets/admin_token` 里的管理令牌，登记本机。

使用 Caddy 自建 CA 时，要把根证书加入每台设备的系统信任，知页才会接受 HTTPS 连接。导出根证书：

```bash
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt ./zhiye-sync-root.crt
```

在 Windows 上，把它导入「受信任的根证书颁发机构」；在 macOS 上，把它加入钥匙串并设为「始终信任」。

数据保存在三个具名卷中：`postgres`（变更日志）、`blobs`（附件原件）和 `caddy_data`（证书）。备份时两份业务数据都要保留，可以用 `docker compose exec postgres pg_dump -U zhiye zhiye_sync` 导出数据库。升级时拉取新源码后再次运行 `docker compose up -d --build`；服务启动时会检查数据库结构版本，不兼容时拒绝启动。

### 直接运行

```bash
cargo build --release -p zhiye-sync-server
```

使用 SQLite，适合单机或测试：

```bash
ZHIYE_SYNC_ADMIN_TOKEN='至少 32 个字符的随机串' target/release/zhiye-sync-server --data /srv/zhiye-sync
```

使用 PostgreSQL：

```bash
target/release/zhiye-sync-server --data /srv/zhiye-sync \
  --database-url 'host=127.0.0.1 user=zhiye dbname=zhiye_sync' \
  --database-password-file /etc/zhiye-sync/db-password \
  --admin-token-file /etc/zhiye-sync/admin-token
```

| 参数 | 环境变量 | 说明 |
|---|---|---|
| `--data <目录>` | | 必填。附件原件放在其中的 `blobs/`；未指定数据库时，`sync.sqlite`（WAL 模式）也放在这里 |
| `--database-url <参数>` | `ZHIYE_SYNC_DATABASE_URL` | 使用 PostgreSQL。可以写 `postgres://` 地址，也可以写 `host=… user=… dbname=…` 形式。首次连接时自动建表，多个实例同时启动也不会冲突 |
| `--database-password-file <文件>` | `ZHIYE_SYNC_DATABASE_PASSWORD_FILE` | 数据库密码文件，避免把密码写进命令行或地址 |
| `--admin-token-file <文件>` | `ZHIYE_SYNC_ADMIN_TOKEN_FILE`，或直接用 `ZHIYE_SYNC_ADMIN_TOKEN` | 管理令牌，至少 32 个字符 |
| `--listen <IP:端口>` | | 默认 `127.0.0.1:8787` |
| `--behind-tls-proxy` | | 监听非回环地址时必须提供。服务本身只提供 HTTP，必须由 HTTPS 反向代理转发 |

数据库还在启动时，服务会每 2 秒重试一次，最多等 60 秒。运行期间如果数据库连接中断，下一次请求会自动重连。

两种存储的行为一致，服务端的全部测试都会在两种存储上各跑一遍（见「验证」）。使用 PostgreSQL 时，同一工作空间的推送按事务级 advisory 锁依次提交，保证变更序号按提交顺序出现，拉取时不会漏掉变更；不同工作空间之间互不阻塞。

服务不依赖官方账号，也不连接外部网络。所有设备都属于同一位用户，可以访问该服务中的全部工作空间。

### 接口

除健康检查外，所有请求都使用 `Authorization: Bearer <令牌>`。请求和响应都是 JSON，字段使用 camelCase。错误响应为 `{"code": "...", "message": "..."}`。

| 方法与路径 | 令牌 | 说明 |
|---|---|---|
| `GET /v1/health` | 无 | 返回 `protocol`、`service`、`version` |
| `POST /v1/devices` | 管理 | `{"name"}` → `{"device", "token"}`。设备令牌只在此返回一次，服务端只保存其 SHA-256 |
| `GET /v1/devices` | 管理 | 设备列表，含最近使用时间和撤销时间 |
| `DELETE /v1/devices/{id}` | 管理 | 撤销设备，之后的请求一律返回 401 |
| `GET /v1/workspaces` | 设备 | 已登记的工作空间 |
| `PUT /v1/workspaces/{id}` | 设备 | `{"name"}`，登记或改名 |
| `POST /v1/workspaces/{id}/push` | 设备 | `{"protocol": 1, "operations": [...]}`，每次 1 至 200 项，每个对象在一次请求中最多出现一次 |
| `GET /v1/workspaces/{id}/changes?since=&limit=` | 设备 | 返回 `{"changes", "nextSeq", "hasMore"}`，每页默认 200 条，最多 500 条 |
| `POST /v1/workspaces/{id}/blobs/missing` | 设备 | `{"hashes": [...]}` → `{"missing": [...]}`，每次最多 1000 个 |
| `PUT /v1/workspaces/{id}/blobs/{sha256}` | 设备 | 正文为原件字节，`Content-Type: application/octet-stream`，最大 100 MiB。内容与 SHA-256 不符时返回 400 `BLOB_MISMATCH` |
| `GET /v1/workspaces/{id}/blobs/{sha256}` | 设备 | 返回原件字节；不存在时返回 404 `BLOB_NOT_FOUND` |

推送操作的结构：

```json
{
  "opId": "6f1c…",
  "objectId": "页面 ID",
  "baseVersion": 3,
  "change": {
    "action": "upsert",
    "page": {"parentId": null, "title": "读书笔记", "icon": "📄", "blocks": [], "trashRootId": null}
  }
}
```

数据库定义为 `"change": {"action": "collection", "collection": {"containerPageId", "properties": [...], "views": [...]}}`。删除为 `"change": {"action": "delete"}`，`baseVersion` 必须是已同步的版本。推送结果为 `{"status": "accepted", "opId", "objectId", "version", "seq"}`，或 `{"status": "conflict", "opId", "objectId", "current"}`。

页面带附件时，`page` 另有 `attachments` 数组和可选的 `cover`；没有附件的页面不输出这两个字段。

单个 JSON 请求最大 32 MiB，单页正文最大 1 MiB，标题 1 至 200 个字符，每页最多 1000 个附件，单个原件最大 100 MiB。

### 第二台设备加入

1. 管理员调用 `POST /v1/devices` 为新设备发放令牌。
2. 新设备调用 `GET /v1/workspaces` 获取工作空间 ID 和名称。
3. 调用 `Store::create_synced_workspace(id, name)` 创建同 ID 的空工作空间，然后执行一次完整同步。

## 本机数据

SQLite 格式 22 新增四张表：

| 表 | 用途 |
|---|---|
| `sync_state` | 拉取游标、是否启用、关联的服务地址，以及上次同步的时间和错误 |
| `sync_objects` | 每个已同步对象的服务端版本、与服务端一致时的状态指纹和删除标记 |
| `sync_outbox` | 已准备、尚未确认的操作、其 `opId` 和所发送状态的指纹 |
| `sync_pending` | 暂时无法写入的远端变化及原因 |

格式 21 的工作空间打开时按既有流程先备份再升级。整库恢复包恢复为新工作空间时会清空这四张表，恢复出的副本不会继续原空间的同步，也不会重放其未发送的操作。

## 验证

```bash
cargo test -p zhiye-sync-protocol -p zhiye-sync-server
```

设置 `ZHIYE_SYNC_TEST_DATABASE_URL` 后，同一套服务端测试会改用 PostgreSQL，每个测试使用独立的 schema；另有一项测试检查多个连接并发推送同一对象时只接受一次、第二个实例能复用已有结构：

```bash
docker run -d --name zhiye-sync-pgtest -e POSTGRES_USER=zhiye -e POSTGRES_PASSWORD=zhiye-test \
  -e POSTGRES_DB=zhiye_sync -p 127.0.0.1:55432:5432 postgres:17-alpine
ZHIYE_SYNC_TEST_DATABASE_URL=postgres://zhiye:zhiye-test@127.0.0.1:55432/zhiye_sync \
```
